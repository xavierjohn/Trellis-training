## Summary

Building the Order Management System with Trellis was efficient overall. The framework's source generators, value objects, and Result<T> pattern provided strong guardrails. A few friction points arose around Maybe<T> property access in specifications and the imperative workarounds needed for Result monadic composition.

## Friction Points

### FP-1: TRLS006 treats Maybe<T>.Value access as error in specification expressions
- **Category:** Workaround Required
- **Severity:** Medium (slowed progress)
- **Context:** Writing `OverdueOrderSpecification` that checks `order.SubmittedAt.Value < cutoff` where `SubmittedAt` is `Maybe<DateTime>`.
- **What happened:** The TRLS006 analyzer flags `Maybe<T>.Value` access as an error, even when preceded by `HasValue` checks in the same expression.
- **Workaround used:** Used `GetValueOrDefault(DateTime.MaxValue)` instead of `.Value`:
  ```csharp
  order.SubmittedAt.GetValueOrDefault(DateTime.MaxValue) < cutoff
  ```
- **Suggested improvement:** Either make TRLS006 flow-sensitive (recognize `.HasValue` guard) or provide a `Maybe<T>.Match()` or `Maybe<T>.Map()` that is analyzer-friendly for specification expressions.

### FP-2: Result monadic composition (ParallelAsync, BindAsync) is difficult to use correctly
- **Category:** Ambiguous API
- **Severity:** Medium (slowed progress)
- **Context:** In `CreateDraftOrderCommand` handler, trying to fetch Customer and Products in parallel using `Result.ParallelAsync`, then compose results with `BindAsync`.
- **What happened:** `Result.ParallelAsync` with async lambdas inside non-async delegates caused compilation errors. `BindAsync` had ambiguity between `Task` and `ValueTask` overloads. Required multiple rewrites.
- **Workaround used:** Rewrote to imperative style with early `if (!result.IsSuccess)` returns instead of fluent chaining.
- **Suggested improvement:** Provide clearer documentation or examples for common composition patterns. Consider providing a `Result.All(task1, task2)` overload that accepts `Task<Result<T>>` directly.

### FP-3: TRLS001 requires discarding Results even in fire-and-forget scenarios
- **Category:** Minor Inconvenience
- **Severity:** Low (minor inconvenience)
- **Context:** In `CancelOrderCommand` handler, calling `product.ReleaseStock()` and `repo.SaveAsync()` where the result is intentionally not needed (best-effort stock release during cancellation).
- **What happened:** TRLS001 requires every `Result` to be consumed. Had to add `_ =` discards for intentionally ignored results.
- **Workaround used:** `_ = product.ReleaseStock(...)` and `_ = await repo.SaveAsync(...)`.
- **Suggested improvement:** This is arguably correct behavior. Perhaps document a pattern for fire-and-forget Result operations, or provide a `.Forget()` extension.

### FP-4: LineItem entity constructor visibility
- **Category:** Workaround Required
- **Severity:** Low (minor inconvenience)
- **Context:** Application layer handler needed to create `LineItem` instances, but the Trellis entity generator made the constructor `internal`.
- **What happened:** Application project couldn't call the generated internal constructor.
- **Workaround used:** Added a `public static LineItem Create(...)` factory method on `LineItem`.
- **Suggested improvement:** Document the recommended pattern for creating entities from outside the Domain assembly, or make entity constructors public by default.

## What Worked Well

- **Source generators** — Zero boilerplate for value objects, aggregates, and entities. `RequiredString<T>`, `RequiredGuid<T>`, `RequiredInt<T>` with attribute-driven validation were excellent.
- **LazyStateMachine<TState, TTrigger>** — Clean state machine integration with EF Core. `FireResult()` returning `Result<TState>` instead of throwing fits perfectly with the Result pattern.
- **SaveChangesResultUnitAsync** — Automatic conflict detection (duplicate key → ConflictError) eliminated manual try/catch around EF Core saves.
- **ApplyTrellisConventions** — Automatic EF Core mapping for all scalar value objects and Money. Only needed explicit config for the composite ShippingAddress.
- **HasTrellisIndex** — Properly resolves Maybe<T> backing fields for database indexes.
- **Authorization pipeline** — `IAuthorize`, `IAuthorizeResource<T>`, and `ResourceLoaderById` provided clean separation of authorization from business logic.
- **AddDevelopmentActorProvider** with `X-Test-Actor` header — Made integration testing with different actors/permissions trivial.
- **API versioning** via namespace convention — Zero configuration, just namespace the controller correctly.
- **Testing infrastructure** — `FakeRepository<T, TId>`, `TestActorProvider`, `WithActor()` scope, and `BeSuccess()/BeFailure()/BeFailureOfType<T>()` FluentAssertions extensions were productive.
- **TRLS003 analyzer** — Catches unchecked `.Value` access on Result, preventing bugs. Easy to suppress in test files with `#pragma warning disable`.

## Suggested New Features

- **Proposed API:**
