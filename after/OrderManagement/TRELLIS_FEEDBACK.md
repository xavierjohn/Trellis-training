# Trellis Feedback — OrderManagement

> Generated by AI while building OrderManagement on 2026-03-10.
> Trellis version: 3.0.0-alpha.104
> AI model: Claude Opus 4.6

## Summary

Trellis provided a cohesive, opinionated framework for building the Order Management service. The ROP pipeline, value objects, and EF Core conventions significantly reduced boilerplate. The main friction was around async lambda disambiguation in ROP chains, and an initial source generator cache issue that turned out to be environmental.

## Friction Points

### FP-1: CA1725 parameter name `ct` vs `cancellationToken`
- **Category:** Ambiguous API / Missing Documentation
- **Severity:** Medium (slowed progress)
- **Context:** Writing handlers with `TreatWarningsAsErrors=true` and `AnalysisLevel=latest-Recommended`.
- **What happened:** The copilot instructions use `ct` as the cancellation token parameter name throughout handler examples. However, CA1725 requires the parameter to match the base interface's name (`cancellationToken`). With warnings as errors, all handlers initially failed to compile.
- **Workaround used:** Changed all handler parameter names from `ct` to `cancellationToken`.
- **Suggested improvement:** Update copilot instructions to use `cancellationToken` in all handler examples since `TreatWarningsAsErrors=true` is the default template configuration.

### FP-2: `Money.Create` throws on invalid input instead of returning Result
- **Category:** Ambiguous API
- **Severity:** Low (minor inconvenience)
- **Context:** Writing domain tests for `Product.TryCreate` with invalid prices.
- **What happened:** `Money.Create(-1m, "USD")` throws `InvalidOperationException` instead of returning a `Result<Money>`. This is inconsistent with the "errors as values" principle — `Money.TryCreate` exists but `Money.Create` is the one used in most examples. A domain test attempting to verify that `Product.TryCreate` rejects negative prices crashed because `Money.Create` threw before reaching the product validation.
- **Workaround used:** Changed the test to assert that `Money.Create` throws, since negative-price prevention happens at the value object level rather than the aggregate level.
- **Suggested improvement:** Consider deprecating `Money.Create` in favor of `Money.TryCreate` to maintain consistency with the ROP approach. At minimum, document clearly that `Create` throws while `TryCreate` returns `Result<Money>`.

### FP-3: `DomainEvents` property is protected on Aggregate
- **Category:** Missing Building Block
- **Severity:** Low (minor inconvenience)
- **Context:** Writing domain unit tests that verify domain events were raised.
- **What happened:** `order.DomainEvents` is protected, so tests cannot directly inspect raised events. The only public API is `IsChanged` (bool), which doesn't tell you *which* events were raised.
- **Workaround used:** Asserted `IsChanged` is true after state transitions, but couldn't verify specific event types or contents.
- **Suggested improvement:** Provide a public read-only `IReadOnlyCollection<IDomainEvent> DomainEvents` accessor, or a `Trellis.Testing` extension method like `aggregate.Should().HaveRaisedEvent<TEvent>()`.

### FP-4: HasIndex with Maybe<T> property requires string-based backing field reference
- **Category:** Missing Documentation
- **Severity:** Medium (slowed progress)
- **Context:** Creating a composite index on `(Status, SubmittedAt)` in OrderConfiguration.
- **What happened:** `builder.HasIndex(o => new { o.Status, o.SubmittedAt })` fails because `MaybeConvention` ignores the `Maybe<T>` CLR property. Had to use string-based column reference `builder.HasIndex("Status", "_submittedAt")` instead.
- **Workaround used:** `builder.HasIndex("Status", "_submittedAt").HasDatabaseName("IX_Orders_Status_SubmittedAt");`
- **Suggested improvement:** Document this limitation in the copilot instructions under the Maybe<T> Property Mapping section. Consider providing a `HasIndexWithMaybe` extension or documenting the exact string pattern for backing field references in indexes.

## What Worked Well

- **`ApplyTrellisConventions`** eliminated all `HasConversion` boilerplate — value objects just worked with EF Core out of the box.
- **`Money` auto-mapped as owned type** — split into Amount + Currency columns automatically with zero configuration.
- **`Specification<T>` composability** — `WhereNone`, `WhereHasValue` extension methods and direct `.Where(spec)` on `IQueryable` made repository queries clean.
- **`ToActionResult` / `ToCreatedAtActionResult`** — single-line controller actions that convert `Result<T>` to proper HTTP responses with RFC 9457 Problem Details.
- **`AddScalarValueValidation`** — automatic JSON deserialization validation for value object types in request DTOs eliminated manual `TryCreate` calls in controllers.
- **`Result.ParallelAsync` + `WhenAllAsync`** — clean parallel fetch pattern for handlers needing multiple independent lookups.
- **`FireResult()` extension for Stateless** — elegant integration of state machine transitions into the ROP pipeline.
- **`SaveChangesResultUnitAsync`** — wraps EF Core save in `Result<Unit>` without exposing row counts the repositories don't need.
- **`FirstOrDefaultResultAsync`** — single-call pattern for "find or return NotFound error" that eliminated boilerplate in every repository.
- **Trellis Analyzers (TRLS001/003/006/007)** — caught unhandled Results, unsafe `.Value` access, and Maybe misuse at compile time. With `TreatWarningsAsErrors`, these were invaluable for correctness.

## Copilot Instructions Feedback

- **§ Handler ROP Pattern:** Examples use `ct` as the cancellation token parameter name, but the template's `AnalysisLevel=latest-Recommended` + `TreatWarningsAsErrors=true` enforces CA1725 which requires `cancellationToken`. All examples should use `cancellationToken`.
- **§ Maybe<T> Property Mapping:** Missing guidance on how to create EF Core indexes that include `Maybe<T>` properties. The section explains that `MaybeConvention` ignores the CLR property but doesn't explain how to reference the backing field in composite indexes.
- **§ EF Core:** The section says "No `MaybeProperty()` call needed" but doesn't mention that `HasIndex` referencing `Maybe<T>` properties will silently fail. Adding an example like `builder.HasIndex("Status", "_submittedAt")` would save significant debugging time.
